# User trip data storage plan

This plan describes how RoamReady should save the trip details shown in the user's mid-fidelity “Plan a trip” screen. The owner-scoped `public.user_trips` schema is now live through [migration 20261029225934_user_trips.sql](../supabase/migrations/20261029225934_user_trips.sql). The API routes and front-end persistence still need implementation; applying the migration did not create any trip rows.

## What the form collects

| Screen field | Required? | Stored field | Validation and purpose |
| --- | --- | --- | --- |
| Where are you going? | Yes | `destination_slug` | Must match an active row in `public.destinations`; store the stable slug, not the display name. |
| When are you traveling? | Yes | `start_date`, `end_date` | Store ISO calendar dates; end date must be on or after start date. |
| What's the trip for? | Yes | `trip_purpose` | Store one of `leisure`, `work`, `study`, or `emergency`. |
| Give your trip a name | No | `trip_name` | Optional label, up to 80 characters. |
| Trip description | No | `trip_description` | Optional note, up to 1,000 characters; tell users not to enter passport, medical, or precise-location details. |

The screenshot's “Your plan will include” categories—entry and documents, money and payments, phones and tech, health, getting there, getting around, safety, and local culture—are generated by the application, so they are not user-entered form data and do not belong in the trip row. Checklist completion can remain session-only in the first version. If the team later needs it to sync across devices, add a separate child table keyed to `trip_id` and protect it with the same owner rule.

The current `frontend/src/main.js` form is a different draft: its destination is hard-coded, it has one optional date, purpose values that do not match the screenshot, an extra solo-experience field, and no trip name or description. Before implementing storage, load active destinations from the API and update the form to the agreed screenshot fields and consistent input names. Do not silently save the extra experience field unless the team keeps it as a product requirement.

## Supabase record

The proposed `public.user_trips` table has one row per saved trip:

- `id`: generated UUID used to open and edit a saved plan.
- `owner_id`: Supabase Auth user UUID; this is the link back to the account.
- `destination_slug`: foreign key to the existing country catalog.
- `start_date` and `end_date`: date range used to tailor the preparation view.
- `trip_purpose`: constrained category from the form.
- `trip_name` and `trip_description`: optional user-provided text with length limits.
- `created_at` and `updated_at`: database timestamps for trip ordering and edits.

Do not copy the user's email into this table. Supabase Auth remains the source of identity, and deleting an Auth account cascades to that account's trip rows. A user can delete an individual trip through the account-protected API.

## Request-to-database workflow

1. The front end requires a registered, signed-in user before saving. Supabase Auth provides the user's access token.
2. The form submits the destination slug, dates, purpose, and optional text to FastAPI with `Authorization: Bearer <access-token>`.
3. FastAPI validates the token with `require_authenticated_user`, validates the request fields, and confirms the destination is active.
4. FastAPI gets `owner_id` from the validated Auth user ID. It must ignore or reject any `owner_id` supplied by the browser.
5. A trip-specific Supabase repository sends the request to PostgREST with the publishable API key and the same validated user's access token. It must not reuse `app/repositories/supabase_rest.py`'s service-role query helper for trip CRUD: a service-role key bypasses RLS.
6. Supabase applies the owner-only RLS policy. The insert policy checks that `owner_id` equals `auth.uid()`; select, update, and delete policies limit affected rows to that same owner.
7. FastAPI returns the saved trip and its generated ID. The front end uses the ID to load or edit the plan; it does not treat `sessionStorage` as the durable record.
8. On sign-out, the page clears the displayed trip state. On a failed save, it keeps the form data visible and offers retry without claiming that the trip was saved.

## Suggested API contract

| Route | Access | Backend behavior |
| --- | --- | --- |
| `POST /api/trips` | Signed-in user | Validate and create a trip owned by the current user; return `201` and the saved record. |
| `GET /api/trips` | Signed-in user | Return only trips owned by the current user, ordered by most recently updated. |
| `GET /api/trips/{trip_id}` | Signed-in user | Return one owned trip; return `404` when it does not exist or is not owned by the caller. |
| `PATCH /api/trips/{trip_id}` | Signed-in user | Validate and update editable fields; never allow the owner to change. |
| `DELETE /api/trips/{trip_id}` | Signed-in user | Delete only the caller's trip and return a clear success response. |

Suggested code locations follow the existing repository layout: `app/api/routes/trips.py` for routes, `app/schemas/trips.py` for request/response validation, and `app/repositories/trips.py` for user-scoped Supabase operations. The Auth dependency should expose both the validated user ID and the bearer token to this repository. Do not make the service-role key available to the browser.

## Privacy and acceptance requirements

- A signed-out request cannot create, list, read, update, or delete trip records.
- Two accounts cannot read or change each other's trips, including by guessing a trip UUID.
- The database derives ownership checks from `auth.uid()` and the API derives `owner_id` from the validated token.
- Purpose values outside the screenshot's four choices are rejected. Invalid dates, unknown destinations, overlong text, and empty required fields receive a clear validation error.
- Optional description is not a place to request passport numbers, health details, exact location, or other unnecessary sensitive data. Do not log complete trip descriptions.
- Saving, editing, listing, and deleting a trip is verified with two separate test accounts before enabling the feature for the demo.
- The form, API, and schema agree on whether dates and purpose are required. The screenshot presents these fields as required; the current frontend marks them optional.

## Implementation sequence

1. Confirm the required date and purpose fields with the team. The applied migration follows the screenshot; the current front end still marks them optional, so any schema changes should use a new migration.
2. Add the Pydantic models, token-carrying Auth dependency, and user-scoped trip repository/API routes.
3. Align the front-end form with the agreed fields and send its Supabase access token to FastAPI.
4. Verify the owner-isolation and validation acceptance requirements with two test accounts; then update the README and demo plan.
